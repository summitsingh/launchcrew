## Complete scope

This connector adds an optional Google Picker intake for one app-authorized file, without replacing existing flows:

- Google Picker user selection with `https://www.googleapis.com/auth/drive.file` scope. Google documents this scope as per-file selected access, but the scope technically permits edits. Product code only calls read-only Drive file metadata, get, export, and download APIs. It never calls create, update, delete, or permissions APIs. See [OAuth web-server](https://developers.google.com/identity/protocols/oauth2/web-server), [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect), [Picker web guidance](https://developers.google.com/workspace/drive/picker/guides/web-picker), and [Drive API auth](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).
- Separate signed-in-only user-initiated Drive authorization-code flow that reuses the EXISTING Google identity OAuth client and secret. Ordinary sign-in stays `openid profile email` only in `backend/auth.py`. Drive consent requests only identity plus `drive.file` necessary to validate subject and drive Picker, online with no refresh token and no offline grant. No sign-in scope is broadened. No GIS browser token client and no tokeninfo introspection are used.
- Owner binding: the backend binds Drive state to the current opaque signed-in session and actor, preserves the actor session without rotation or demo replacement, and rejects state, actor, session, code, audience, issuer, expiry, subject, or granted scope mismatches before any file read. OpenID nonce is validated by Authlib authorize_access_token from saved state during ID token parsing; source does no separate nonce comparison. Authlib validated ID token and userinfo are used, plus explicit exact audience (`GOOGLE_CLIENT_ID`) and subject (`google:<sub>`) checks. Granted scope accepts only openid, email or canonical userinfo email form, profile or canonical userinfo profile form, plus exact drive file scope; unrelated, broad, duplicate, or ambiguous alias pairs fail closed. See [OAuth scopes](https://developers.google.com/identity/protocols/oauth2). Missing, ambiguous, or mismatched audience or identity fails closed. Only Google actors may use Drive; demo placeholder and non-Google actors fail closed even when Drive config exists.
- One-time grant: the short-lived access token is returned to the same signed-in browser ONLY to drive official Picker, over a no-store same-origin session-bound one-time POST claim. No token appears in URL, query, fragment, log, cookie, persistent DB, localStorage, sessionStorage, or public receipts. The backend keeps a tightly bounded ephemeral in-memory grant (plaintext only until first claim, then a nonreversible digest bound to actor, session, and expiry) and consumes it on one selected-file POST. A per-process lock atomically claims and consumes the grant before provider work and never spans provider I/O. Grants live in process memory only. A restart or a rolling update that routes authorize and claim to different tasks fails closed with consent required and needs reauthorization via Connect Drive and choose file again. No sticky routing is claimed. The selected-file POST proves its token is the exact server-issued token for this client and current actor and session; subject-only userinfo or a browser-supplied token from another client is insufficient. Mismatched, expired, or replayed grants are refused before Drive API calls.
- Only the stated file ID and resource key may be read. The API accepts no URLs and no workspace ID. Workspace is derived server-side from the LaunchCrew actor. Anonymous use fails closed, and foreign workspace use fails closed. A file ID alone does not prove a fresh Picker selection server-side; `drive.file` only permits app-authorized files the user opened for this app. The latest UI selection display stays local browser behavior only.
- Supported demo set: Google Docs export to plain text (`application/vnd.google-apps.document` exported as `text/plain`) and plain text download (`text/plain`). All other types fail closed, including photos, PDFs, HTML, video, and binary. No photos in Picker views or server handling.
- Explicit bounds, enforced before allocation: max 200000 bytes per file, max 10000 text chars for parsing, max 3 provider requests per import as an upper bound (file import uses at most metadata plus content; OAuth validation uses ID token during callback, not tokeninfo), max 20 suggestions, max 500 chars per suggestion via the shared parser. Content-Length is checked before reading. Downloads stream with a hard cap.
- Closed refusals: arbitrary URLs, redirect following, wrong host, missing scope, broad scope, duplicate scope, ambiguous alias pair, offline refresh grant, expired token, wrong audience, wrong issuer, expired ID claim, wrong Google account, missing or ambiguous audience or identity, state or session replay or expiry, nonce mismatch via Authlib, nonselected file, trashed file, ID mismatch, unsupported MIME, oversize content, non-text bytes, and deceptive Content-Type.
- Privacy-safe transport: provider access tokens travel only in POST JSON bodies and Authorization Bearer headers, never in URLs. No token in URL, logs, persistence, or responses except the one-time Picker claim body. No raw capability URL or key, file bytes, or full private file body in public receipts or logs. Success returns a sanitized file title, MIME label, generic selection context, and bounded unconfirmed parsed text lines for owner UI only. No provider file ID, resource key, or token appears in responses, receipts, or logs.
- Bounded candidate facts as UNCONFIRMED with `drive_file` provenance. Never auto-confirm, never auto-add to Memory, never auto-publish, and never present provider text as verified marketing facts. The existing owner fact confirmation flow is reused. Public receipts stay free of provider identifiers and full file bodies.
- Public app stays keyless for this connector: no Meta calls, no model calls, no database writes for file content. Product works without Drive configuration, with a clear optional unavailable state. Pasted-text import still works.

## Practical named-test-user demo path now

This path uses synthetic test identities only, for example `synthetic-test-user-01` and `synthetic-test-user-02` in mocked tests. No personal names, emails, accounts, or asset filenames are used.

1. Operator configures the Drive inputs in server environment only (see Configuration). No value goes in source, commits, logs, or docs. Google console needs the extra exact Drive callback URI, Drive and Picker APIs, consent scope, restricted API key and project number, named test users, and possible External Testing or public review.
2. Owner signs in with existing Google identity sign-in. Demo placeholder mode and non-Google actors cannot use Drive intake; status reports unavailable with reason `auth_required`, config and suggestions require sign-in.
3. Owner opens owner-input mode, sees Drive status, and chooses Connect Drive and choose file. The browser navigates same-origin to `GET /api/drive-import/authorize`, the backend preserves the signed-in session and redirects to Google consent for identity plus `drive.file` only, online with no refresh token.
4. Google redirects to the exact HTTPS callback `GET /api/drive-import/callback` with code and state. The backend validates state, actor, session, code, audience, issuer, expiry, subject, and granted scope before any file read, creates a one-time session-bound grant, clears the pending OAuth binding without rotating the sign-in cookie, and redirects to `/?drive=authorized` with no token in URL.
5. The browser claims the short-lived token once via `POST /api/drive-import/picker-token` (no-store, same-origin, session-bound), holds it in memory only, and launches official Picker filtered to Google Docs and plain text with the public API key and app ID.
6. Owner selects one file in Picker. The UI holds the selection ephemerally and posts only file ID, optional resource key, and the exact server-issued token in the POST body to `POST /api/drive-import/suggestions`. The backend verifies the token digest against the grant for the current actor and session, consumes the grant, then reads metadata for app-authorized files, enforces MIME and size bounds, downloads or exports bounded text with no redirects and Bearer header only, parses with the shared unconfirmed parser, and returns bounded unconfirmed parsed lines with Drive file provenance and sanitized title context. File ID alone never proves fresh Picker selection. Each file read needs a fresh authorization.
7. Owner edits suggestions and explicitly adds chosen lines as unconfirmed allowed claims, then explicitly confirms each in the existing fact form. Only confirmed values with `drive_file` source can become evidence in a later run. Unconfirmed values stay suggestions.

## Configuration inputs, exact names without values

Public Drive inputs live only in server process environment. They are never in source or commits. The backend serves only the public Picker subset to the signed-in frontend via `GET /api/drive-import/config`. No secret and no token is served.

- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`: existing identity sign-in credentials, reused for the separate Drive authorization-code flow. Identity login stays `openid profile email` only. Drive consent requests identity plus `drive.file` only, online with no refresh token. Never served to frontend.
- `GOOGLE_DRIVE_API_KEY`: public browser API key used by Picker. Served to frontend. No secret value here.
- `GOOGLE_DRIVE_APP_ID`: Cloud project number used by Picker. Served to frontend. No secret value here.
- `PUBLIC_BASE_URL`: exact HTTPS LaunchCrew origin. Drive callback is `PUBLIC_BASE_URL` plus `/api/drive-import/callback` and must be registered exactly in the Google console as a prerequisite.

When any required input is missing, `GET /api/drive-import/status` reports `available` false with reason `drive_not_configured`, `GET /api/drive-import/config` returns 503, and Drive authorize, callback, token, and suggestions return 503. When inputs exist but the actor is demo placeholder or non-Google, status reports `available` false with reason `auth_required`, config returns 401 for demo or 403 for non-Google, and authorize, token, and suggestions return 401 for demo or 403 for non-Google, with no provider calls. Pasted-text import still works.

## Bounded workflow and failure states

- `GET /api/drive-import/status`: Google-actor bound status with `available`, `configured`, `live_verified` false, `scope`, `supported_mime_types`, `max_bytes`, `max_requests`, and `reason` (`ok`, `drive_not_configured`, or `auth_required`).
- `GET /api/drive-import/config`: Google-actor bound public Picker config only (API key, app ID, bounds, scope, MIME types). 503 when unconfigured. 401 when demo sign-in is required, 403 for non-Google actor.
- `GET /api/drive-import/authorize`: signed-in Google-only user-initiated redirect to Google consent for identity plus `drive.file`, online with no refresh token. Preserves the sign-in session without rotation. 401 for demo, 403 for non-Google, 503 when unconfigured.
- `GET /api/drive-import/callback`: exact HTTPS callback that validates state, actor, session, code, audience, issuer, expiry, subject, and granted scope before any file read, creates a one-time grant, and redirects to `/?drive=authorized` with no token in URL. Consent failures return generic 403 with no provider details.
- `POST /api/drive-import/picker-token`: no-store same-origin session-bound one-time claim that returns the short-lived access token in JSON body only. Second claim, expired grant, or wrong actor or session returns 403 and requires reauthorization.
- `POST /api/drive-import/suggestions`: body carries `file_id`, optional `resource_key`, and `drive_token` in POST JSON only, never in URL. Verifies the token is the exact server-issued token for the current actor and session via nonreversible digest, consumes the grant, then reads at most metadata plus content. Stateless apart from the ephemeral in-memory grant, no database writes for file content. Response carries `status` unconfirmed, `source` drive_file, `product_fact_source` drive_file, `file_title` sanitized, `mime_type`, `selection_context` Drive file selection, bounded unconfirmed parsed `suggestions` with `confirmed` false, drop counts, and `parser_version` drive-import/v1.
- Failure codes use generic details with no IDs, tokens, bytes, titles, or file bodies: Drive consent required (including wrong audience, wrong issuer, expired claim, wrong Google account, missing or ambiguous identity, state or session mismatch, expired or replayed grant, or foreign token) or file unavailable or not selected is reported as 403, LaunchCrew sign-in required is reported as 401, too large is reported as 413, unsupported type or invalid selection is reported as 422, provider error is reported as 502, and unavailable is reported as 503. The UI maps these to actionable hints and always offers pasted-text import.
- Rolling update overlap: grants live in process memory only with a per-process lock. When tasks overlap during a rolling update, authorize and claim can land on different tasks; the claim fails closed with consent required and needs reauthorization via Connect Drive and choose file again. No sticky routing is claimed.
- Concurrent single winner: simultaneous Picker claims and simultaneous file reads allow only one winner; losers fail closed with consent required, no resend, and no extra provider reads.
