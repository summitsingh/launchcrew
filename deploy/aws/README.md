# LaunchCrew AWS deployment code, review only, not applied

Status: Code review only. No AWS account access, no apply, no IAM change, no DNS, no secret, no paid resource, no deployment. This directory is in a separate deployment-code worktree, based on main 4bb295d, and it does not touch the integration owner checkout or main.

## What this code does, and what it does not do

Implemented in code, reviewable here:
- Separate migration job: containers/api.Containerfile no longer runs alembic at runtime startup. Runtime CMD is uvicorn only, through containers/api-entrypoint.sh. Migration is a separate image, containers/migrate.Containerfile, CMD alembic upgrade head only, no server, for a separate Fargate one-off task, with its own IAM migration role in deploy/aws/fargate.yaml. Runtime database identities have no DDL in deploy/aws/db-roles.sql, migration is the only schema change path.
- TLS-capable API container: containers/api-entrypoint.sh decodes TLS_CERT_B64 and TLS_KEY_B64, from Secrets Manager via ECS task secrets, to /tmp/tls/cert.pem and /tmp/tls/key.pem, mode 600, without logging any certificate, key, or base64 value, then serves TLS on port 8443. If TLS_CERT_FILE and TLS_KEY_FILE are set to existing files instead, those files are used directly, for local TLS tests. If LAUNCHCREW_REQUIRE_CONTAINER_TLS=1, set in the Fargate API task definition, and material is missing, the task fails closed, exit 1, instead of starting plain HTTP. If only one file, or only one base64 variable, is set, exit 1. A dry-run mode prints the uvicorn command instead of execing it, then deletes any files decoded in dry-run mode. Plain HTTP on port 8000 is local development only, and must never be used for a public deployment.
- Web TLS sidecar, implemented: containers/web-proxy.Containerfile builds a Node image that runs web/tls-proxy.mjs through containers/web-proxy-entrypoint.sh, as user node. The entrypoint decodes TLS_CERT_B64 and TLS_KEY_B64 to /tmp/tls files, mode 600, without logging any certificate, key, or base64 value, and exits 1 when no certificate material is present. There is no plain HTTP proxy mode. The proxy listens on 0.0.0.0:8443 with TLS and proxies only to a loopback target, default http://127.0.0.1:3000, and refuses to start for a non-loopback TLS_PROXY_TARGET. The web app container, in the same Fargate task, binds 127.0.0.1:3000 only, via the task definition HOSTNAME override, and is never exposed directly. The ALB web target group points at the web-proxy container, port 8443, not at the app.
- Removed gate parameters: the old WebTlsReady and ApiTlsReady parameters were fail-closed gates, not implementations. They are removed from the template, and the template now has 11 parameters, matched by deploy/aws/parameters.example.json. The removed gates must not be presented as proof of TLS. Proof is the sidecar code, the entrypoint code, and local TLS tests with ephemeral certificates, plus the real cloud verification listed below.
- Verified database TLS with explicit modes: backend/store.py implements LAUNCHCREW_DB_TLS_MODE with three cases. Verify-full requires sslmode=verify-full in DATABASE_URL and an existing DATABASE_SSL_ROOTCERT file, for any host. Local allows only localhost, 127.0.0.1, or the compose hostname db, and rejects a non-local host. Unset allows local hosts only and requires verify-full for any other host. Unknown mode values raise. No certificate value, password, or secret is logged, only the requirement that failed. The Fargate API and migration task definitions set verify-full with DATABASE_SSL_ROOTCERT=/app/rds-ca-bundle.pem. Local compose.yaml sets local for api and for the separate migrate service, so the local demo DATABASE_URL using host db still passes. This enforcement applies to both API and migration connections, because backend/migrations/env.py shares the backend SQLAlchemy engine.
- Separated database identities: deploy/aws/db-roles.sql creates a runtime role with SELECT, INSERT, UPDATE, DELETE plus schema USAGE plus sequence USAGE and SELECT, no DDL, no CREATE, no TRUNCATE, no REFERENCES, no TRIGGER, and a migration role with schema CREATE plus full table and sequence rights. Default privileges are FOR ROLE the migration identity, which is the identity that creates the tables through alembic. ALTER and DROP never appear as table privileges, because PostgreSQL does not define them. The file is run once, with the master database user, in a separately authorized provisioning run. No password is in the file. Passwords are supplied via Secrets Manager, one secret per database identity. The template passes separate RuntimeDbUrlSecretArn and MigrationDbUrlSecretArn values, and each task role reads only its own secret. The web role has no database or provider-secret access, with an empty policy list in the template. The master database username is separated to launchcrew_master, used for initial creation only. Database role verification against a disposable instance is PENDING independent verification, and no result is claimed here.
- Fixed task counts: deploy/aws/fargate.yaml sets DesiredCount 1 for api and web, with no autoscaling resource, no AutoScaling policy, and no scaling target. Any scaling change requires a template change and a new review, it cannot happen by default.
- Log retention: 7 days, set in the template for api, web, and migration log groups, before services start, per the bounded logs requirement. No request bodies, headers, or secrets are logged by this code, and that rule must be checked in application code before deployment.
- Resource tags: Project LaunchCrew, Environment demo, TeardownBy 2026-11-09, on VPC, subnets, ECR repos, RDS, cluster, and ALB, in the template. Tags are not a cost cap, they are an inventory and teardown aid.
- Teardown plan in code: deploy/aws/teardown.sh, dry-run by default, prints deletion steps in reverse dependency order, with no AWS call in dry-run mode, and requires an explicit --confirm flag before any AWS call. Teardown order: services, listeners, target groups, ALB, task definitions, cluster, RDS and snapshots, ECR images, log groups, IAM roles, VPC and subnets, budget, then Cloudflare record, only if created, then verification of no recurring charges. Teardown is required after Nov 4 and no later than Nov 9, 2026.

## Remaining gap, stated plainly, not hidden

The RDS CA bundle must be placed at /app/rds-ca-bundle.pem at image build time, in the API image and in the migration image. The task definitions already set DATABASE_SSL_ROOTCERT to that path with LAUNCHCREW_DB_TLS_MODE=verify-full. If the bundle is missing at that path in real deployment, backend/store.py fails closed and the tasks do not start. No bundle checksum or download URL content is stated here, because none was verified in this work. Before provisioning, the bundle placement must be added to the image builds and verified, or provisioning must supply it by another reviewed path, otherwise deployment stays blocked on database TLS.

## Inputs, explicit and unapproved

- Region: us-east-1, recommended, NOT confirmed, nothing provisioned in it. The template region is the deployment region at apply time, it is not a default approval in this file.
- Domain: there is no DomainName parameter in the template. The template outputs the ALB DNS name only. A demo domain record, if ever wanted, requires separate explicit authorization, and no DNS record is created by this code.
- Certificate: ACM certificate ARN, parameter AcmCertificateArn, no default, no certificate value in this file.
- Image URIs: ApiImageUri, WebImageUri, WebProxyImageUri, MigrationImageUri, parameters, no default, images must be built from the Containerfiles in this worktree, with no key, .env, credential, or receipt history in the image, run as non-root, API and migration as UID 10001, web app and web proxy as user node.
- Database users: DatabaseUsername, default launchcrew_master, master for initial creation only. The master password comes only from MasterDbPasswordSecretArn, JSON key password, used only for initial RDS creation, never read by runtime or migration tasks. Runtime and migration identities are created separately by deploy/aws/db-roles.sql and use their own secrets, RuntimeDbUrlSecretArn and MigrationDbUrlSecretArn, no value in this file, placeholder only. Each secret connection string value must include sslmode=verify-full, otherwise the tasks fail closed.
- TLS material: TlsSecretArn, Secrets Manager ARN with JSON keys tls-cert-b64 and tls-key-b64, base64 PEM, placeholder only, no value in this file.
- Cost cap and budget: BudgetLimitUsd, parameter, no approved default, no amount is implied here. A spending cap is a user choice after seeing the estimate, in the AWS deployment proposal, recommended Fargate $17.10 for 7 days, $28.57 for 12 days, App Runner revised with NAT egress $19.51 for 7 days, $32.69 for 12 days. A value of 0 in a parameters file is a placeholder that must be replaced, it is not an approval.
- Auth: AUTH_ENABLED is false in the template API task definition, matching the current code default, health auth disabled_demo, approval_by demo_placeholder. Real sign-in is a separate gate, with provider credentials supplied securely outside the repo, and HTTPS callback URLs, and it is not claimed as live here.

## What requires real cloud verification, and cannot be proven statically or locally

- CloudFormation template validation and apply, in a real account, with real parameters, after a separate deployment tap and a filled cost cap.
- ALB HTTPS listener with a real ACM certificate, Cloudflare Full strict origin verification, custom domain verification, and certificate renewal.
- ALB HTTPS target groups, with API TLS on 8443 and web proxy TLS on 8443 verified by health checks, with real certificate material supplied through TlsSecretArn, and the web app reachable only through the proxy on loopback.
- RDS private connectivity, no public port, database TLS verify-full from both API and migration tasks, with the real RDS CA bundle present at /app/rds-ca-bundle.pem in both images, and rejection of an invalid certificate, which cannot be proven with a local trust-auth database.
- Separate migration execution, with the migration IAM role and the migration database identity, before runtime tasks start, and runtime tasks starting with CRUD only and no migration rights, in a real VPC.
- ECR image pull, Fargate task start, log group retention, budget alarm, and teardown deletion, with actual resource identifiers and actual cost, reported before provisioning, after provisioning, and after teardown, without secrets.
- Real identity-provider sign-in, session behavior, and public access boundary, only in a separately authorized deployment.
- NAT egress, if the App Runner alternative is ever revisited: App Runner VPC-connected services lose public internet egress, and require a NAT Gateway in private connector subnets, per AWS App Runner docs, with revised costs above. This Fargate template does not use App Runner, and Fargate tasks in public subnets with a public IP reach the internet through the internet gateway, with no NAT required, but that must still be verified in a real VPC run.
