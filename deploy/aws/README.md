## What this code does, and what it does not do

Implemented in code, reviewable here:
- Separate migration job: containers/api.Containerfile no longer runs alembic at runtime startup. Runtime CMD is uvicorn only, through containers/api-entrypoint.sh. Migration is a separate image, containers/migrate.Containerfile, CMD alembic upgrade head only, no server, for a separate Fargate one-off task, with its own IAM migration role in deploy/aws/fargate.yaml. Runtime database identities have no DDL in deploy/aws/db-roles.sql, migration is the only schema change path.
- TLS-capable API container: containers/api-entrypoint.sh decodes TLS_CERT_B64 and TLS_KEY_B64, from Secrets Manager via ECS task secrets, to /tmp/tls/cert.pem and /tmp/tls/key.pem, mode 600, without logging any certificate, key, or base64 value, then serves TLS on port 8443. If TLS_CERT_FILE and TLS_KEY_FILE are set to existing files instead, those files are used directly, for local TLS tests. If LAUNCHCREW_REQUIRE_CONTAINER_TLS=1, set in the Fargate API task definition, and material is missing, the task fails closed, exit 1, instead of starting plain HTTP. If only one file, or only one base64 variable, is set, exit 1. A dry-run mode prints the uvicorn command instead of execing it, then deletes any files decoded in dry-run mode. Plain HTTP on port 8000 is local development only, and must never be used for a public deployment.
- Web TLS sidecar, implemented: containers/web-proxy.Containerfile builds a Node image that runs web/tls-proxy.mjs through containers/web-proxy-entrypoint.sh, as user node. The entrypoint decodes TLS_CERT_B64 and TLS_KEY_B64 to /tmp/tls files, mode 600, without logging any certificate, key, or base64 value, and exits 1 when no certificate material is present. There is no plain HTTP proxy mode. The proxy listens on 0.0.0.0:8443 with TLS and proxies only to a loopback target, default http://127.0.0.1:3000, and refuses to start for a non-loopback TLS_PROXY_TARGET. The web app container, in the same Fargate task, binds 127.0.0.1:3000 only, via the task definition HOSTNAME override, and is never exposed directly. The ALB web target group points at the web-proxy container, port 8443, not at the app.
- Removed gate parameters: the old WebTlsReady and ApiTlsReady parameters were fail-closed gates, not implementations. They are removed from the template. The duplicate BudgetLimitUsd and BudgetNotifyEmail parameters were also removed: the app template now has 12 parameters, matched by deploy/aws/parameters.example.json, and the exact budget name plus its topic, policy, and subscription live only in deploy/aws/foundation.yaml. The removed gates must not be presented as proof of TLS. Proof is the sidecar code, the entrypoint code, and local TLS tests with ephemeral certificates, plus the real cloud verification listed below.
- Verified database TLS with explicit modes: backend/store.py implements LAUNCHCREW_DB_TLS_MODE with three cases. Verify-full requires sslmode=verify-full in DATABASE_URL and an existing DATABASE_SSL_ROOTCERT file, for any host. Local allows only localhost, 127.0.0.1, or the compose hostname db, and rejects a non-local host. Unset allows local hosts only and requires verify-full for any other host. Unknown mode values raise. No certificate value, password, or secret is logged, only the requirement that failed. The Fargate API and migration task definitions set verify-full with DATABASE_SSL_ROOTCERT=/app/rds-ca-bundle.pem. Local compose.yaml sets local for api and for the separate migrate service, so the local demo DATABASE_URL using host db still passes. This enforcement applies to both API and migration connections, because backend/migrations/env.py shares the backend SQLAlchemy engine.
- Separated database identities: deploy/aws/db-roles.sql creates a runtime role with SELECT, INSERT, UPDATE, DELETE plus schema USAGE plus sequence USAGE and SELECT, no DDL, no CREATE, no TRUNCATE, no REFERENCES, no TRIGGER, and a migration role with schema CREATE plus full table and sequence rights. Default privileges are FOR ROLE the migration identity, which is the identity that creates the tables through alembic. ALTER and DROP never appear as table privileges, because PostgreSQL does not define them. The file is applied by the isolated bootstrap task with the master database user, never by runtime or migration tasks. No password is in the file. Passwords arrive only as ECS-injected Secrets Manager values held in task memory. The template passes separate RuntimeDbUrlSecretArn, MigrationDbUrlSecretArn, and TlsSecretArn values, and each task's execution role may read only its own secrets: the api execution role reads the runtime URL plus TLS material, never master or migration; migration reads only the migration URL; bootstrap reads master plus both URLs; verify reads only the runtime URL. The bootstrap controller re-checks these exact secret bindings and execution roles from live state before any one-off task starts. Task roles carry no secret fetch at all, because the app reads injected environment, never the Secrets Manager API. Existing roles are rebound only with the ownership stamp and no superuser, create, replication, or membership takeover risk; server-side statement logging stays outside the job, so it stays off for secret-bearing statements. The web role has no database or provider-secret access, with an empty policy list in the template. The master database username is separated to launchcrew_master, used for initial creation only. ## Remaining gap, stated plainly, not hidden

The official regional RDS us-east-1 bundle is vendored at backend/assets/rds-us-east-1-bundle.pem and copied byte-for-byte to /app/rds-ca-bundle.pem at image build time, in both the API image and the migration image, with a pinned SHA256 build check and mode 644; see docs/db-ca-bundle.md for provenance, checksum, rotation, and region scope. The Debian ca-certificates package is installed only for ordinary outbound HTTPS and is never substituted for the RDS bundle. The task definitions already set DATABASE_SSL_ROOTCERT to that path with LAUNCHCREW_DB_TLS_MODE=verify-full, and backend/tests/test_db_ca_bundle.py checks the hash, the three self-issued root names, and the wiring statically. If the bundle is missing at that path in real deployment, backend/store.py fails closed and the tasks do not start. No live database TLS handshake has been proven in this work: the local trust-auth database cannot prove verify-full or invalid-certificate rejection, so that live check stays an open deployment gate, listed below with the other cloud verifications.
